# Minecraft 科技模组 Web 结构演示方案讨论总结

## 一、背景

该讨论起源于 Minecraft 科技模组教程的表达问题。

在大型科技整合包中，很多结构、流程和机器逻辑并不需要完整实机环境来展示。传统图文教程和教学视频通常依赖游戏内截图、录屏或实机搭建画面，这种方式虽然真实直观，但信息负担较重：画面中会混入 UI、光影、地形、视角、人物操作、环境杂讯等内容。对于“展示一个结构如何搭建”“解释某个流程如何运作”这类目标来说，实机画面显得过于笨重。

相比之下，机械动力的 Ponder 和 AE2 游戏内指南中的 3D 结构展示更接近一种“干净的技术图解”。它们弱化了游戏实景，突出结构、部件、方向、层级和逻辑关系，因此更适合作为教学表达。

由此引出了一个核心问题：如果在 Astro 这类博客框架中写 Minecraft 科技模组教程，是否可以不用实机截图，而是用 Web 中的交互式 3D 结构演示来表达内容。

## 二、目标

该方向的目标不是制作一个完整的 Minecraft Web 客户端，也不是还原一个可游玩的世界，而是构建一种用于博客和技术文章的 Minecraft 科技模组结构表达方式。

它的重点是：

展示 AE2、机械动力等科技模组中的机器、网络、结构和流程；
在网页中呈现可旋转、可缩放、可分层、可标注的 3D 结构；
用结构文件和资源包生成干净的教学图，而不是依赖游戏截图；
最终为博客文章提供类似 AE2 Guide 或 Create Ponder 的交互式说明能力。

因此该方向的核心定位可以概括为：

**Minecraft 科技模组知识表达系统，而不是 Minecraft 网页渲染器本身。**

## 三、核心定位

经过讨论后，方案逐渐从“寻找一个 Minecraft 3D viewer”收敛为“为科技模组教程设计一套结构化展示组件”。

该系统应该服务于技术写作，而不是服务于玩家生存建造。

所以它更关心：

结构是否清楚；
部件之间的关系是否能被看懂；
流程是否能被分步骤展示；
是否能在文章中低成本复用；
是否能适配 AE2、Create 等模组资源。

它不优先追求：

完整世界加载；
大型建筑投影；
真实游戏环境还原；
复杂实体行为模拟；
玩家视角操作复刻。

这意味着它应该更接近“Web 版 GuideME / Ponder DSL”，而不是“网页版 Minecraft”。

## 四、文件格式选择

讨论中重点比较了 `.litematic` 与 `.nbt` 两种结构文件。

`.litematic` 是 Litematica 使用的投影文件格式，常用于大型建筑、生存服投影、生电工程和玩家建筑迁移。它支持多区域、丰富元数据、投影辅助等能力，适合保存和复现大型结构。

但对于科技模组博客教程来说，`.litematic` 的许多能力并不是刚需。科技教程通常只需要展示小规模结构，例如一个 AE2 网络节点、一个机械动力传动结构、一个自动加工单元、一个局部机器组合。结构规模通常不大，目标也不是让读者照着投影建造完整建筑。

因此讨论中更倾向于优先使用 Minecraft 原版 Structure NBT，也就是 `.nbt` 结构文件。

`.nbt` 的优势在于：

它是 Minecraft 原版结构系统使用的格式；
可以通过原版结构方块导出；
机械动力蓝图也与 NBT 结构体系关系更近；
数据结构相对直接，适合 Web 端解析；
更符合“小结构教学演示”的需求。

因此初步结论是：

**该项目应优先支持 Structure NBT，而不是优先支持 Litematic。**

Litematic 可以作为未来扩展格式，而不是第一阶段核心输入。

## 五、Web 客户端需要解析什么

对于 `.nbt` 结构文件，Web 客户端首先需要解析的是结构中的方块数据，而不是完整游戏逻辑。

基础渲染所需信息主要包括：

结构尺寸；
palette，也就是方块状态表；
blocks，也就是每个方块的位置和对应状态；
block entity 数据，例如箱子、接口、控制器等可能携带的附加信息；
必要时还包括实体数据。

但对于第一阶段目标来说，最关键的是：

```text
NBT 结构文件
→ 方块位置
→ 方块 ID / BlockState
→ 对应模型
→ 对应贴图
→ WebGL / Three.js 渲染
```

也就是说，NBT 只告诉系统“哪里有什么方块”。真正决定“这个方块长什么样”的，是 Minecraft 的资源系统。

## 六、真正的难点：资源包与模组资产

讨论中明确了一个重要判断：NBT 解析并不是最难的部分，真正困难的是 Minecraft 模型与资源包管线。

对于原版方块，很多已有 viewer 或 renderer 已经可以比较好地处理，因为原版资源稳定、公开、格式统一。

但科技模组的核心方块来自模组自身，例如：

```text
ae2:controller
ae2:interface
ae2:energy_acceptor
create:shaft
create:gearbox
create:mechanical_bearing
create:deployer
```

这些方块的模型、blockstate、贴图都在对应 mod 的 jar 包中。

因此系统必须解决：

如何从 mod jar 中提取 assets；
如何加载 `assets/<modid>/blockstates`；
如何加载 `assets/<modid>/models`；
如何加载 `assets/<modid>/textures`；
如何处理模型继承、贴图引用、方块朝向、变体状态；
如何把 Minecraft 的 JSON 模型转换为 Three.js 可渲染对象。

所以该项目真正有价值的部分并不仅仅是“解析 NBT”，而是：

**建立一套面向科技模组的 Web 资源包加载与渲染管线。**

这也是它和普通原版 schematic viewer 的关键区别。

## 七、已有项目调研方向

讨论中提到过几个相关项目，它们分别对应不同层级。

MineRender 更适合快速展示单方块、物品、生物或简单结构，可以作为第一阶段参考。它偏“图鉴式展示”，适合做博客中的轻量插图，但不足以直接实现复杂教程场景。

Lodestone 更接近底层 Minecraft Web 渲染 SDK。它基于 Three.js，支持 Minecraft 风格场景渲染，也提到支持自定义资源包和投影格式。它适合作为后续结构渲染层的候选基础，但需要额外封装，不能直接等同于博客组件。

craftmatic 更像 schematic / structure 工具链，适合处理结构文件转换、解析、生成等任务。它可能更适合作为构建工具或辅助管线的一部分。

prismarine-viewer 更偏向完整 Minecraft 世界或机器人视角渲染，能力较强，但对于小型教学结构而言可能过重。

Web-Ponder 最接近“机械动力 Ponder 的 Web 化体验”，但它的维护状态、兼容性和可复用程度需要进一步评估。它的主要价值可能不是直接拿来用，而是研究其场景模型、动画组织方式和 DSL 设计思路。

## 八、AE2 官方 Guide 的启发

后续讨论中进一步关注了 AE2 官方指南系统。

AE2 的游戏内指南并不是发明了一个全新的结构格式，而是通过 GuideME 一类的指南系统，在 Markdown / Guide 页面中嵌入特殊组件，例如 GameScene、BlockImage、ImportStructure 等。

它的思路大致是：

```text
Guide Markdown
→ GameScene
→ ImportStructure
→ Structure NBT / SNBT
→ Minecraft 客户端渲染
```

这说明 AE2 官方的路线本质上也是：

**文本说明 + 结构文件 + 场景组件 + Minecraft 渲染系统。**

这一点和当前项目设想高度吻合。

从 AE2 的设计中可以得到一个重要启发：博客中的组件不应该直接暴露 Three.js 细节，而应该提供更语义化的结构组件，例如：

```text
<MCScene>
  <Structure src="ae2-network.nbt" />
  <Camera preset="isometric" />
</MCScene>
```

或者：

```text
<BlockImage id="ae2:controller" />
```

也就是说，文章作者应该使用面向教学的标签，而不是直接编写底层 3D 场景代码。

## 九、开发顺序

讨论后形成的开发顺序大致如下。

第一阶段是单方块展示。目标是先实现类似 MineRender 的能力，在 Astro / MDX 页面中渲染一个 Minecraft 方块或物品。例如展示 `ae2:controller`、`create:shaft`、`create:gearbox`。这一阶段重点不是结构文件，而是打通资源加载、blockstate 解析、模型解析和贴图渲染流程。

第二阶段是科技模组资源包适配。系统需要能够加载原版资源，也需要加载 AE2、Create 等 mod jar 中的 assets。这个阶段会决定项目是否真正适合科技模组教程。若只能显示原版方块，该项目的价值会大幅下降。

第三阶段是 Structure NBT 解析。系统需要读取 `.nbt` 或 `.snbt` 文件，解析结构尺寸、palette 和 blocks，并将其中的方块状态映射到 Web 渲染模型。完成后，博客中就可以嵌入小型空间结构，而不需要实机截图。

第四阶段是 Astro / MDX 组件封装。目标是让作者可以在文章中低成本使用，例如：

```mdx
<MCBlock id="create:shaft" />

<MCStructure src="/structures/create-fan.nbt" />
```

这一阶段重点是写作体验，而不是单纯渲染能力。

第五阶段是教学增强能力。包括默认等轴测视角、可拖动旋转、缩放、分层查看、隐藏空气方块、显示边框、局部高亮、添加箭头、添加文字标注等。这些能力会让它从“结构查看器”变成“教程插图系统”。

第六阶段才是 Ponder 化。也就是加入时间轴、镜头运动、结构逐步出现、方块高亮、部件动画、文字旁白等能力。这个阶段难度最高，因为它不只是渲染问题，而是一个叙事系统问题。

## 十、最终架构设想

经过讨论后，较合理的架构可以概括为：

```text
Astro / MDX 博客文章
        ↓
Minecraft 教学组件层
        ↓
场景描述 DSL
        ↓
Structure NBT / 单方块 / 手写结构
        ↓
Minecraft 资源加载系统
        ↓
BlockState / Model / Texture 解析
        ↓
Three.js / Lodestone 等渲染层
        ↓
Web 交互式 3D 结构演示
```

其中，最上层服务于写作，中间层服务于教学语义，底层才是渲染技术。

## 十一、项目的核心价值

该项目的核心价值不在于“网页上显示 Minecraft 方块”，而在于把科技模组教程中的结构知识变成一种可复用、可交互、可维护的表达单元。

传统教程依赖截图，截图是静态结果；
该方案依赖结构文件，结构文件是可解析数据。

传统视频依赖实机录制，录制成本高；
该方案依赖场景描述，后续可以复用和修改。

传统图文教程只能展示某个角度；
该方案可以旋转、缩放、分层和高亮。

因此，该方向更像是：

**面向 Minecraft 科技模组的 Web 版 GuideME / 轻量 Ponder 系统。**

它尤其适合 AE2、机械动力这类强结构、强流程、强空间关系的模组教学。

## 十二、当前结论

目前较明确的技术路线是：

优先选择 Structure NBT 作为结构输入；
优先支持 AE2 和 Create 这类科技模组资源；
先从单方块渲染做起，再做小型结构展示；
Lodestone 可以作为渲染层候选，但需要评估其对 NBT 和自定义资源包的实际支持；
MineRender 可作为早期参考，但不宜作为最终架构的上限；
Web-Ponder 可作为 Ponder 化阶段的参考对象；
最终目标应是一个适合 Astro / MDX 博客使用的 Minecraft 科技结构演示组件。

一句话总结就是：

**该项目不是为了把 Minecraft 搬进网页，而是为了把科技模组里的结构逻辑，从截图里解放出来。**
